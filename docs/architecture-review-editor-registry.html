SwallowNote · 基于 deep module 设计原则的架构扫描

设计词汇:Module(模块) · Interface(接口) · Depth(深度) · Seam(接缝) · Adapter(适配器) · Leverage(杠杆) · Locality(局部性)

候选 1:Editor Registry — 编辑器注册中心

Strong

涉及文件

src/components/Editor.tsx · src/components/editors/*.tsx · src/stores/pluginEditor.ts · src/lib/utils/fileTypeUtils.ts

问题

Editor.tsx 是一个 shallow module — 它的 interface(4 层 if-else,6 种 props 形状)几乎和它的 implementation(只是把 props 传给具体编辑器)一样复杂。新增一个编辑器需要改 12 处、跨 7 个文件。文件类型路由名义上集中在 detectFileType,实际在 7+ 处重复,且判定方法不一致(.md 后缀 vs 正则 vs type === 'plugin')。搜索集成通过 editorType 字符串字面量在 5 处 if-else 分发。这是典型的开闭原则违反。

方案

创建 EditorRegistry deep module — 一个编辑器注册中心。每个编辑器(内置 + 插件)通过声明式注册接入,声明:支持的文件类型匹配器、组件 lazy loader、props 适配器、搜索能力、flush 能力、工具栏能力。Editor.tsx 退化为一个 ~20 行的查表渲染器:查 registry → 取 editor descriptor → 用统一 EditorProps 渲染。新增编辑器只需写一个注册模块,0 处现有文件改动。

收益

  • Leverage:Editor.tsx 从 ~600 行条件树 → ~20 行查表,调用方只需学一个 resolveEditor(filename) 接口
  • Locality:新增编辑器的所有知识(类型匹配、props 适配、搜索、flush)集中在一个注册文件,而非散落 7 个文件
  • 测试:registry 接口成为测试面 — 注册一个 mock editor → 断言 resolveEditor 返回它 → 断言 props 适配正确
  • 开闭原则:新增编辑器 = 新增注册模块,0 处现有文件改动

候选 2:统一 EditorProps 契约

Strong

涉及文件

src/components/editors/MarkdownEditor.tsx · src/components/editors/CodeEditor.tsx · src/components/DiffViewer/*.tsx · src/components/Editor.tsx

问题

6 个编辑器组件有 6 套不同的 props 签名:MarkdownEditor 用 {content, onChange?},CodeEditor 用 {content, filename, onChange?, className?, scrollToLine?},DiffViewer 用 {diffContent},ConflictResolver 用 {repoPath, repoName, ...}。调用方(Editor.tsx)靠条件 spread 打补丁:{...(isShim ? { filename } : {})}。MarkdownEditor 甚至绕过 props 从 store 自己拿 filename。接口不统一导致 Editor.tsx 无法用单一调用点渲染所有编辑器。

方案

定义统一的 EditorProps deep interface,每个编辑器通过 Adapter 适配到这个接口。统一接口包含:tab: EditorTab(完整 tab 上下文)、onChange: (content: string) => void、onFlush?: () => Promise<void>。各编辑器的特有需求(filename、repoPath 等)通过 Adapter 从 tab 上下文中提取,而非调用方手动传。DiffViewer/ConflictResolver 这类只读/特殊编辑器,通过 canEdit: false 能力声明跳过编辑接口。

收益

  • Leverage:Editor.tsx 用 <EditorComponent {...editorProps} /> 单一调用点,不再条件 spread
  • Locality:各编辑器的 props 转换逻辑集中在自己的 Adapter,而非调用方
  • 测试:EditorProps 契约成为测试面 — 传入标准 tab fixture → 断言 adapter 产出正确 props

Before / After

BEFORE — 6 套 props + 条件 spread

// Editor.tsx — 6 种调用方式
<MarkdownEditor content=... onChange=... />
<CodeEditor content=... filename=...
  onChange=... scrollToLine=... />
<PluginEditor content=... onChange=... />
<MindMapEditor content=... onChange=...
  {...(isShim ? {filename} : {})} />
<DiffViewer diffContent=... />
<ConflictResolver repoPath=...
  repoName=... initialSelectedFile=... />

AFTER — 统一 EditorProps

// Editor.tsx — 单一调用点
const desc = registry.resolve(tab)
const props = desc.adapter(tab)
<desc.component {...props} />

// 统一接口
interface EditorProps {
  tab: EditorTab
  onChange: (c: string) => void
  onFlush?: () => Promise<void>
}

候选 3:EditorSearchAdapter — 搜索能力适配器

Worth exploring

涉及文件

src/components/editors/useEditorSearchIntegration.ts · src/components/FindReplacePanel.tsx · src/components/EditorToolbar.tsx

问题

useEditorSearchIntegration 内部有 5 处 if (editorType === 'codemirror') 分支,为绕过 Hooks 规则同时调用两个 hook 再用三元选一个。FindReplaceEditorType 和 EditorSearchType 在两个文件各定义一遍。FindReplacePanel 还自己判断 isCodeMirror 来决定 UI 差异(正则/全词选项)。新增一个支持搜索的编辑器需要改 5 处 if-else + 2 处类型定义 + 1 处 UI 分支。

方案

定义 EditorSearchAdapter interface,各编辑器实现自己的搜索适配器(BlockNoteSearchAdapter、CodeMirrorSearchAdapter)。Adapter 声明能力:supportsRegex: boolean、supportsWholeWord: boolean。useEditorSearchIntegration 退化为 const search = registry.resolveSearch(tab),无 if-else。可作为 Candidate 1 的子能力,也可独立实施。

收益

  • Locality:BlockNote 搜索逻辑在 BlockNoteSearchAdapter,CodeMirror 在 CodeMirrorSearchAdapter
  • Leverage:useEditorSearchIntegration 从 ~140 行 → ~30 行,无 if-else
  • 测试:Adapter 接口成为测试面,可独立测试各编辑器的搜索实现

Top 推荐

候选 1 + 候选 2 合并实施 — Editor Registry 与统一 EditorProps 是天然耦合的:registry 需要 EditorProps 契约才能工作,EditorProps 需要 registry 来选择正确的 adapter。单独做任一个都会留下半成品。

实施顺序:先定义 EditorProps + EditorDescriptor 接口(候选 2)→ 创建 EditorRegistry 并迁移内置编辑器(候选 1)→ Editor.tsx 退化为查表渲染器 → 搜索适配器(候选 3)作为后续独立深化。

风险:Editor.tsx 是启动关键路径上的模块,改动需保持行为不变。建议 TDD:先写 characterization test 锁定现有行为,再逐步迁移。MindMapEditor shim 和 PluginEditor 的 isShim 分支是最容易出问题的边界。
